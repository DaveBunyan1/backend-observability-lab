# Python Logging Module

## Previous Logging Setup

The previous logging setup evolved incrementally from simple `print()` statements to manually writing log messages to a file for a set of simple CRUD endpoints.

The initial implementation used `print()` statements to observe what was happening during request processing. This worked for sequential requests, but became less useful once concurrent traffic was introduced because messages from different requests could become difficult to associate with the request that produced them.

To improve this, request IDs were introduced. A unique request ID was generated by the HTTP middleware and included in application log messages so that multiple messages belonging to the same request could be correlated.

The logging implementation was then changed from `print()` statements to manually opening and writing to a log file:

```python
with open("logs/logs.log", "a") as file:
    file.write(f"{request_id} Received request: GET /jobs\n")
```

This provided persistent log files that could be examined after the application had run, but introduced several problems.

### Issues with the Previous Implementation

#### Malformed log entries

When concurrent requests attempted to write to the log file, some log entries became malformed. This made the resulting log difficult to read and potentially unreliable for later analysis.

#### Repetitive file-writing code

Every log message required explicitly opening the file and writing to it:

```python
with open("logs/logs.log", "a") as file:
    file.write(...)
```

As the number of log messages increased, this became cumbersome and duplicated the same file-writing logic throughout the application.

#### Repetitive request IDs

Every message also needed the request ID to be explicitly included:

```python
file.write(f"{request_id} Found job: {job_id}\n")
file.write(f"{request_id} Deleted job: {job_id}\n")
file.write(f"{request_id} Job not found: {job_id}\n")
```

This made the application code increasingly concerned with the mechanics of logging rather than the event being logged.

These limitations motivated the move to Python's `logging` module.

---

## Current Logging Implementation

Python's `logging` module has now been introduced to replace the manual file-writing implementation.

The logging system is configured using `logging.config.dictConfig()`. A `RotatingFileHandler` is used to write log records to the log file.

The application also uses `logging.LoggerAdapter` to attach the request ID to log records.

The HTTP middleware generates the request ID and creates the adapter:

```python
adapter = logging.LoggerAdapter(
    logger,
    {"request_id": request_id},
)

request.state.logger = adapter
```

Application code can then log messages without manually including the request ID:

```python
request.state.logger.info("Found job")
```

This separates the event being logged from the contextual information associated with the request.

At this stage, only `request_id` is being automatically attached as logging context. Other contextual information, such as `job_id`, HTTP method, and path, has deliberately not yet been added to the logging context.

This is intended to keep the current implementation simple while providing an opportunity to introduce additional logging concepts when they become necessary.

---

## Concurrent Logging

The new logging implementation was tested using concurrent simulated requests.

The previous manual file-writing implementation produced malformed log entries under concurrent traffic. After switching to Python's `logging` module, the concurrent test produced intact log records.

The log messages are still interleaved because multiple requests are executing concurrently. This is expected. The request ID allows messages belonging to the same request to be identified despite the interleaving.

For example:

```text
6e0704a7... Received request: GET /jobs/002
6e0704a7... Found job: 002
5da0477e... Received request: DELETE /jobs/002
5da0477e... Deleted job: 002
```

The messages from different requests are interleaved, but each individual record remains intact and the request IDs allow the records to be correlated.

This addressed the malformed-log problem observed with the previous implementation.

## Benchmark Comparison

The API already records request processing time using the `X-Process-Time` response header.

After replacing manual file writes with Python's `logging` module, the same benchmark was run again to determine whether the change introduced a performance regression.

The benchmark used the same concurrency levels as the baseline:

- 30 concurrent users
- 100 concurrent users
- 1,000 concurrent users

Each level was run 10 times.

All benchmark runs completed successfully for both implementations.

### Comparison

The logging implementation did not produce an observable performance regression in this benchmark.

At 30 concurrent users, the results were very similar:

- Mean latency: 22.66 ms → 22.50 ms
- P99 latency: 36.52 ms → 34.92 ms
- Standard deviation: 5.31 ms → 5.59 ms

At higher concurrency, the logging implementation produced lower measured latency:

| Users | Mean Change | P99 Change | Std Dev Change |
| ----: | ----------: | ---------: | -------------: |
|    30 |       -0.7% |      -4.4% |          +5.3% |
|   100 |      -10.5% |     -24.3% |         -18.4% |
| 1,000 |      -11.4% |     -10.4% |          -9.1% |

The largest measured difference occurred at 100 concurrent users, where P99 latency decreased from 143.12 ms to 108.38 ms.

These results do not establish that Python's logging implementation itself makes the application faster. Benchmark results can vary between runs due to factors outside the logging implementation. However, they do show that replacing manual file writes did not introduce an observable performance regression under the tested workload.

## What Was Learned

The progression from `print()` statements to Python's logging module demonstrated several increasingly important requirements for application observability.

```text
print()
  ↓
Persistent log file
  ↓
Request IDs
  ↓
Python logging
  ↓
LoggerAdapter
```

Each change addressed a limitation discovered through experimentation rather than being introduced in advance.

The main lessons so far are:

- `print()` is useful for basic observation during development, but becomes difficult to manage as the application and workload become more complex.
- Manually writing log files provides persistence but duplicates file-handling logic throughout the application.
- Concurrent requests make correlation between log messages important.
- Request IDs provide a simple way to associate multiple log records with the same request.
- Python's `logging` module removes the need for application code to manage log-file writes directly.
- `LoggerAdapter` allows contextual information such as `request_id` to be attached to log records without repeatedly including it in every log message.
- Replacing manual file writes with the logging module eliminated the malformed log records observed during the previous concurrent logging experiment.
- The logging change did not introduce an observable performance regression in the benchmark.

There are still questions that have deliberately not been addressed yet, including how additional context such as `job_id` should be handled, how logging context should behave across different execution boundaries, and whether additional information such as timestamps or log levels is required for meaningful analysis.

## Next Step

The background workload will now be evolved beyond simply making CRUD requests.

The simulated users will begin triggering jobs that perform different types of work. This will create more realistic application behaviour and produce logs containing different outcomes, durations, and execution paths.

The purpose of the next stage is not to add every available logging feature, but to create a workload that makes the logs useful to analyze.

As new limitations become apparent, additional logging concepts can then be introduced to address them.
